# 高频追问与答案（对着本项目的真实实现）

> 用法：每条答案都能指到具体文件，被追问时打开代码讲，比背结论可信得多。

---

## 1. 用户身份是怎么保证的？为什么不用请求头传 userId？

早期是客户端自己传 `X-User-Id`，等于谁都能冒充别人。现在改成**服务端签发 JWT**：
登录成功后签发（`common/JwtUtil`），请求带 `Authorization: Bearer <token>`，
`auth/AuthInterceptor` 验签解析出 userId 写进 `common/UserContext`（ThreadLocal），
Controller 从上下文取，**全项目不再读任何客户端传来的身份**。

两个细节：① 拦截器语义是"可选认证"——匿名放行、无效 token 直接 401，
保留"读接口公开、写接口需登录"的语义；② `afterCompletion` 里必须清 ThreadLocal，
Tomcat 线程复用，不清会串号。

## 2. Redis 和 MySQL 数据不一致怎么办？

架构是「Redis 先应答 → MQ → MySQL 落库」，是**最终一致**而非强一致。三道保障：
① 发布端 `publisher confirm` + `returns` + `mandatory`，消息没到交换机/路由不到队列都会有日志；
② 消费端幂等（捕获唯一索引冲突），重复投递不会重复写；
③ **对账定时任务**（`service/ReconcileTask`，每 10 分钟）：以 MySQL 为准把互动集合与计数回填 Redis。

对账刻意做成**只增不删**：因为对账那一刻可能存在"已写 Redis、消息还在队列里"的关系，
整体重建会把它抹掉。代价是修不了"Redis 有、MySQL 无"（消息丢失/进 DLQ），那需要人工看 DLQ。

## 3. MQ 消息丢了、重复了、积压了怎么办？

- **丢**：三环节设防——生产端 confirm（本次落地）、Broker 队列+消息持久化、消费端 AUTO ack（处理成功才确认）；
  再加对账兜底。
- **重复**：重复投递无法从根上消除（Broker 分不清"没处理"和"处理了没确认"），只能消费端幂等——
  `t_note_like` 的唯一索引捕获 `DuplicateKeyException` 后跳过。
- **积压**：扩容消费者 / 批量写入 / 降级非核心 / 生产端限流，管理台看 Ready 曲线设告警。
- **失败消息**：本地重试 3 次（1s/2s 退避）后 reject，进对应的死信队列 `*.dlq`（P1-6），
  不会无限重投堵死队列。

## 4. 缓存穿透/击穿/雪崩分别怎么解决的？

- **穿透**（查不存在的数据）：查库为空也缓存一个**空对象**，TTL 只有 60 秒
  （见 `NoteService.rebuildWithLock`），避免每次击穿到库。
- **击穿**（热点 key 过期瞬间）：`SET key 1 NX EX 10` 抢分布式锁，只有抢到的线程回源重建，
  其余等待后重读缓存；双重检查避免重复回源。
- **雪崩**（大量 key 同时过期）：TTL = 基础 1800s + **0~300s 随机抖动**，
  把过期时刻打散。Redis 整体挂掉靠降级兜底。

## 5. 幂等是怎么做的？为什么用 Lua，不用 MULTI 或 synchronized？

点赞要"判断有没有点过 + 写入 + 计数"三步。三步不原子：在"点赞两步之间"插进"取消两步"，
会让关系和计数**永久漂移**（先出现 -1 再被钳位成 0）。

用 **Lua** 把三步合并成一次原子执行（`InteractService` 的 6 个脚本）。
- 不用 `synchronized`：只在单实例有效，多实例部署失效。
- 不用 `MULTI`：事务里无法"读后分支判断"（SADD 返回 0 还是 1 决定要不要 INCR）。
- 不用"先查后写"：有竞态窗口。

MySQL 的 `UNIQUE(user_id, note_id)` 作**兜底**（Redis 可能宕机丢数据），
但它只能管"这行重不重"，管不住旁边计数多加——所以是兜底而不是第一道闸。

## 6. 为什么事务里不能直接发 MQ？

事务回滚**撤不回已经发出去的消息**——会产生"幽灵消息"：库里没这笔数据，消费者却收到事件。
解法是把发送**挪到事务提交之后**（`common/TransactionHelper` 封装 `afterCommit` 注册），
`NoteService.publish` / `CommentService.add` 里 MQ 发送和 Redis 副作用都在提交后执行。

残留风险：进程在"提交成功"与"afterCommit 执行"之间崩溃仍会丢副作用，靠对账任务兜底。

## 7. Feed 用推还是拉？为什么大V要区别对待？

纯推（写扩散）：发布时写给每个粉丝的收件箱，**读快但写放大**，千万粉大 V 发布一次就是千万次写。
纯拉（读扩散）：读时聚合所有关注人的内容，**写省但读慢**。

本项目用**推拉结合**：普通作者推给粉丝收件箱；粉丝数超阈值（`xhs.feed.big-v-fans-threshold`）
的作者只写自己的发件箱 `feed:outbox:{authorId}`，粉丝读关注页时归并「收件箱 + 所关注大V的发件箱」。
两个来源的 score 都是毫秒时间戳，直接归并排序。

另外收件箱按条数裁剪（`xhs.feed.keep`，默认 100），否则 ZSet 无限膨胀。

## 8. 热榜为什么需要时间衰减？

只累加的话**早期爆款永久霸榜**。用半衰期指数衰减：
`score = 基础分 × 0.5^(龄期小时 / 半衰期)`，基础分取 DB 真实计数（点赞×1 + 评论×5 + 收藏×2），
由 `service/HotRankTask` 每 10 分钟整体重算。

- 为什么要定时重算：实时 `ZINCRBY` 累加会累积误差，重算能把期间增量按 DB 真实计数一并纳入。
- 已知副作用：老内容分数衰减到接近 0 后，一次实时点赞的 `+1` 会让它瞬间冲榜，
  直到下次重算拉回。彻底解决要么让 addHeat 也按龄期加权，要么缩短重算周期。

## 9. 限流怎么做的？固定窗口有什么问题？

Redis 固定窗口：每秒一个计数 key 做 `INCR`，超过阈值返回 429，首次写入时设 2 秒过期防残留。
key 里带**主体维度**（`rate:limit:u{userId}:{分类}:{秒}`，匿名按 IP）与接口分类，
阈值全部 yml 可配。Redis 故障时 fail-open（放行），避免限流组件拖垮全站。

固定窗口的**致命缺陷是边界突刺**：临界的两秒内可以过 2 倍阈值流量。
进阶用滑动窗口或令牌桶（Redisson `RRateLimiter`）。

**一个容易踩的坑**：限流要用身份，就必须把认证拦截器排在限流**之前**（`WebConfig` 里注册顺序即执行顺序）。

## 10. 搜索为什么不用 MySQL 的 LIKE？ES 上做了哪些事？

`LIKE '%关键词%'` 无法用索引（前缀通配），只能全表扫描，且没有相关度排序。
改用 ES 倒排索引：发笔记 → MQ → `EsConsumer` → 写索引；搜索走 ES，异常时回退 MySQL LIKE。

在这之上做了三件事：
- **IK 中文分词**：默认 `standard` 把中文按**单字**切分，无意义；改成建索引 `ik_max_word`、
  搜索 `ik_smart`（插件固化进 `es/Dockerfile`，避免容器重建丢失）。
- **`multi_match` 加 `operator: and`**：IK 词典没收录的词会退化成单字，默认 `or` 会导致
  "搜『清补凉』命中只含『凉』的笔记"这类误召回。
- **`search_after` 游标分页**：`from/size` 在深分页时每个分片都要取 `from+size` 条再归并。
  排序用 `[_score desc, note_id asc]`（`note_id` 是索引里专为排序加的数值字段，
  因为 **ES 8 默认禁止对 `_id` 排序**）。

## 11. 你用 `X-User-Id` 改 JWT，那前端怎么办？token 过期呢？

前后端一起改（硬切换）：登录响应从"裸 user"变成 `{token, user}`，
前端存 token、请求头改发 `Authorization: Bearer`。
**不做兼容回退**——若同时接受 `X-User-Id` 作为兜底，等于认证可被绕过，白改。

token 过期时拦截器返回**真 HTTP 401**，前端 axios 拦截器捕获后清登录态并提示重新登录
（业务错误仍是 HTTP 200 + body 里带 code，两者分开处理）。

## 12. 这个项目里你印象最深的问题/bug 是什么？（讲踩坑最能体现真实）

可以挑这三个，都是真实发生并有记录的：

1. **序列化不匹配导致功能静默失效**：写侧 Lua 用 `StringRedisTemplate` 写的是裸字符串 `3`，
   读侧 `fillStatus` 却用 JSON 序列化的 `RedisTemplate` 做 `isMember`，成员变成带引号的 `"3"`，
   于是**"已点赞"状态恒为 false**。不报错、不抛异常，只是永远 false。
   更隐蔽的是同一批 key 的 `mergeCounts` 读计数**恰好正常**（Jackson 能解析裸数字），
   所以"一个读路径正常"完全不能证明另一个也正常。Redis 被填满后才暴露。
2. **降级兜底掩盖了上游故障**：搜索的 `try/catch` 把 ES 的异常吞掉、静默降级到 MySQL。
   我第一遍验证时看到"有结果返回"就以为 ES 生效了，实际根本没走 ES
   （ES 8 禁止对 `_id` 排序 → 查询 400 → 被吞 → 降级）。教训：**验证必须确认走的是主路径**，
   这次是靠"响应里有没有游标"识别出来的。
3. **测试基建的坑**：Testcontainers 的 `@Container` 声明在**基类**上时，每个测试类会重启容器、
   映射端口变化，而 Spring 上下文是跨类缓存的、仍指向旧端口 → 第二个测试类开始 Redis 全部超时。
   改用 singleton 容器模式（静态块启动）后解决。

## 13. 密码怎么存的？

BCrypt（`spring-security-crypto`），库里存 60 字符哈希。同一明文每次哈希不同（自带随机盐），
比对用 `matches()`。存量 8 个用户的明文密码做了一次性迁移。
未保留"明文匹配成功再升级"的兼容分支——那会让明文逻辑永远留在代码里。

## 14. 如果让你继续做，你会做什么？

按优先级：
1. **把对账做成双向修复**（现在只补 Redis 缺的，修不了"消息丢失导致 MySQL 少"），
   并给 DLQ 配告警。
2. **关注链路 Redis 化**（现在唯一还走 MySQL 同步写的互动），复用 like 的 MQ 管道。
3. **热榜 addHeat 按龄期加权**，消掉"老内容被一次点赞顶上榜首"的跳变。
4. **健康检查分组**：ES 属降级可依赖，不该拖垮 readiness。
5. **DB 迁移工具**（Flyway）——当前 `init.sql` 单真源够用，等 schema 开始频繁演进再迁。
6. **补齐优化前后的压测对照数据**（见 [PERF.md](PERF.md)，目前只有限流场景的验证数据）。
