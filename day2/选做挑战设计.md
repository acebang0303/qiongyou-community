# Day2 选做挑战设计：评论列表缓存的容量问题与改造方案

> **挑战原文**（《Day2-实训手册-热点查询Redis缓存》第 296 行）：
> 如果某篇笔记评论量极大（上万条），整列表缓存会有什么问题？你会怎么改？
> （提示：只缓存第一页 / 分页缓存）
>
> **前置任务**（手册第八节）：评论列表接口 `GET /api/notes/{noteId}/comments` 接入 Redis，
> Key 为 `comment:list:{noteId}`，TTL 5 分钟，发评论后先写库再删缓存。

本文基于 `../day0/xhs-backend` 的实际代码与实测结果编写，不含对源码的改动。

---

## 一、现状复述

当前实现（`../day0/xhs-backend/src/main/java/com/xhs/service/CommentService.java:38-52`）是**整列表缓存**：

```java
public List<CommentVO> listByNote(Long noteId) {
    String key = RedisKeys.commentList(noteId);
    List<CommentVO> list = (List<CommentVO>) redisTemplate.opsForValue().get(key);
    if (list == null) {
        list = commentMapper.selectByNote(noteId);
        if (list != null) {
            redisTemplate.opsForValue().set(key, list, COMMENT_CACHE_MINUTES, TimeUnit.MINUTES);
        }
    }
    if (CollectionUtils.isEmpty(list)) {
        return Collections.emptyList();
    }
    return list;
}
```

对应 SQL（`CommentMapper.java:14-16`）**没有 LIMIT**，一次取走该笔记的全部评论：

```sql
SELECT c.id, c.user_id, u.nickname, u.avatar, c.content, c.create_time
FROM t_comment c JOIN t_user u ON c.user_id = u.id
WHERE c.note_id = #{noteId} ORDER BY c.create_time ASC
```

在评论量小的场景下这个实现在 Day2 的验收标准上是合格的。问题只在数据量涨到上万条后才暴露。

## 二、上万条评论时，整列表缓存会出什么问题

按严重程度排序。

### 2.1 大 key：阻塞 Redis 单线程（最本质的问题）

Redis 执行命令是**单线程**的。一个 value 的读写会独占事件循环，期间**所有其他客户端的请求排队等待**。

按实测单条 `CommentVO` 的 JSON 体积估算（见附录 A）：

| 场景 | 单条体积 | 1 万条列表 |
| --- | --- | --- |
| 短评论（如「收藏了！下周就去」） | ≈ 150 字节 | **≈ 1.5 MB** |
| 长评论（`content` 上限为 `varchar(500)`） | ≈ 400+ 字节 | **≈ 4 MB** |

两点放大因素：

1. **本项目启用了 Jackson 类型信息**（`RedisConfig.java:33` 的 `activateDefaultTyping`）。每个数组元素都会被包成 `["com.xhs.vo.CommentVO",{...}]`，类型名本身就有 21 字节，整体体积再膨胀约 30%。
2. **`DEL` 比 `GET` 更危险**。Redis 5.0 默认 `lazyfree-lazy-user-del no`，删除大 key 时**同步**释放内存。本项目 `add()` 里每次发评论都会删掉这个几 MB 的 key（`CommentService.java:73`），热点笔记下等于反复触发同步内存回收。

> 量级参照：业界通常把 value > 10 KB 视为大 key，> 1 MB 视为严重。几 MB 的单 value 需要立即处理。

### 2.2 缓存击穿 → 重建风暴（业务上最致命）

`add()` 里发一条评论就 `delete` 掉**整个列表**：

```java
commentMapper.insert(comment);
noteMapper.update(... comment_count + 1 ...);
redisTemplate.delete(RedisKeys.commentList(noteId));   // 整列表一起失效
```

于是热门笔记上：**每发一条评论，就有一个人要承担"查上万行 + 序列化上万个对象 + 写回几 MB"的代价**。评论越活跃的笔记，重建越频繁，而重建本身又最慢——典型的正反馈恶化。

Day5 引入的 `note:lock:{id}` 分布式锁只解决"多个请求同时重建"，**并不降低重建本身的代价**，也无法减少重建频次。

### 2.3 序列化 / 网络 / 数据库三头开销

- **未命中**：MySQL 一次返回上万行（几 MB 网络传输）→ Jackson 序列化上万个对象（CPU + 内存尖峰）→ 写入 Redis（几 MB 网络）
- **命中**：从 Redis 取回几 MB → 反序列化上万个对象 → 序列化进 HTTP 响应体
- 而**用户实际只需要第一页的 20 条**。99% 的序列化、传输、内存都是白做的

### 2.4 内存放大与淘汰

每篇热门笔记都在 Redis 里常驻一份完整列表。内存被大批"没人看的第 100 页数据"占满后触发淘汰策略，反而可能把真正热点的 key 挤出去，命中率崩塌。

### 2.5 排序稳定性（正确性隐患）

`ORDER BY c.create_time ASC` 没有唯一字段兜底。一旦出现两条评论时间戳相同（批量导入、并发写入很常见），MySQL **不保证**返回顺序稳定，同一条评论可能在两次请求里出现在不同位置。缓存的引入会把这个不稳定的结果**固化 5 分钟**。

## 三、改造方案

### 前提：当前接口根本没有分页参数

`listByNote(Long noteId)` 是全量签名，`CommentController.list` 也只接收 `noteId`。
**"只缓存第一页"的前提是代码里先有"页"这个概念**——所以分页是缓存策略的前置条件，不是反过来。这一步必须先做。

### 方案 A：只缓存第一页（最小改动，性价比最高）

```java
// RedisKeys.java
/** 评论列表缓存：comment:list:1:1 */
public static String commentList(Long noteId, int page) {
    return "comment:list:" + noteId + ":" + page;
}
```

- **Key**：`comment:list:{noteId}:1`
- **Value**：仅前 20 条，几 KB，彻底脱离大 key 区间
- **失效**：`add()` 仍然只删 1 个 key，逻辑一个字不用改
- **覆盖率**：评论区绝大多数访问只到第一页，热点覆盖率高
- **代价**：第 2 页起直查 DB

### 方案 B：分页缓存前 N 页 + 页码阈值

```java
private static final int DEFAULT_PAGE_SIZE = 20;
private static final int MAX_CACHE_PAGE = 5;
private static final long CACHE_MINUTES = 5;
private static final long EMPTY_CACHE_MINUTES = 1;   // 空列表短过期，防穿透

public List<CommentVO> listByNote(Long noteId, int page) {
    if (page < 1) {
        return Collections.emptyList();
    }
    int offset = (page - 1) * DEFAULT_PAGE_SIZE;

    // 冷页：直接查库，不缓存
    if (page > MAX_CACHE_PAGE) {
        return queryDb(noteId, offset);
    }

    String key = RedisKeys.commentList(noteId, page);
    List<CommentVO> list = (List<CommentVO>) redisTemplate.opsForValue().get(key);
    if (list == null) {
        list = queryDb(noteId, offset);
        long ttl = list.isEmpty() ? EMPTY_CACHE_MINUTES : CACHE_MINUTES;
        redisTemplate.opsForValue().set(key, list, ttl, TimeUnit.MINUTES);
    }
    return list;
}
```

- **Key**：`comment:list:{noteId}:{page}`，单页几 KB
- **阈值**：`page ≤ 5` 走缓存，`page > 5` 直查数据库——承接了绝大部分流量，又不为冷数据浪费内存
- **必须固定每页条数**。如果 `pageSize` 由前端随意传入，key 空间会变成 `5 页 × 最多 50 种 size = 250 个组合/笔记`，**失效时无法枚举要删哪些 key**（`KEYS comment:list:*` 会阻塞整个实例，禁止使用）

### 方案 C：游标分页 + 只缓存首页

```sql
-- 第一页（无游标）
SELECT ... FROM t_comment c JOIN t_user u ON c.user_id = u.id
WHERE c.note_id = ? ORDER BY c.id DESC LIMIT 20;

-- 后续页（游标 = 上一页最后一条的 id）
SELECT ... FROM t_comment c JOIN t_user u ON c.user_id = u.id
WHERE c.note_id = ? AND c.id < ? ORDER BY c.id DESC LIMIT 20;
```

- 扫描行数**恒等于每页条数**，第 5000 页和第 1 页耗时几乎相同，从根上消灭深分页
- 新评论插在最前也不会造成偏移，**不会重复、不会漏数据**
- **但游标值不可预测**（取决于上一页内容），无法作为 key 分量，所以**只能缓存第一页**
- 接口需改为 `list(noteId, lastId?)`，`lastId` 为空即第一页；不能再传 `page`（游标分页本身不知道页号）
- 依赖 `(note_id, id)` 索引（见 3.4）

### 3.3 三个方案对比

| | 缓存 key 数 | 深分页 | 失效代价 | 前端改动 | 数据一致性 |
| --- | --- | --- | --- | --- | --- |
| A 只缓存首页 | 1 | 未解决 | 删 1 个 | 传 page/size | offset 偏移 |
| B 前 5 页 + 阈值 | 5 | 未解决 | 删 ≤5 个 | 传 page/size | offset 偏移 |
| **C 游标 + 首页缓存** | **1** | **✅ 彻底解决** | **删 1 个** | 传 lastId | **✅ 无偏移** |

**方案 C 的一个反直觉推论**：B 想"缓存前 5 页承接流量"，是因为 **offset 分页下** `LIMIT 20,20`、`LIMIT 80,20` 越翻越慢，所以要多缓存几页。
一旦换成游标，"第 2 页慢"这个前提就消失了——它和第 1 页一样快，**根本不需要缓存**。B 的 5 个 key 退化成 C 的 1 个 key，还顺带解决了数据偏移问题。

### 3.4 索引前提

实测当前表结构：

```sql
PRIMARY KEY (`id`),
KEY `idx_note` (`note_id`)        -- 只有单列，没有 (note_id, id)
```

游标 SQL 高效的前提是能走 `(note_id, id)`。InnoDB 的二级索引叶子节点会**附带主键**，所以 `idx_note(note_id)` 在物理上已等价于 `(note_id, id)`，理论上够用；但优化器是否选用需要 `EXPLAIN` 确认。稳妥做法是显式加：

```sql
ALTER TABLE t_comment ADD INDEX idx_note_id (note_id, id);
```

## 四、失效策略：排序方向决定一切

这是整份设计里最容易做错的地方——**失效策略能不能偷懒，完全取决于排序方向**。

当前代码是**正序** `ORDER BY c.create_time ASC`（`CommentMapper.java:16`），而评论区产品的常规 UX 是倒序。这个差别改变了所有结论：

| 排序 | 新评论落在 | offset 分页下的影响 | 能否"不主动删 + 短 TTL 兜底" |
| --- | --- | --- | --- |
| `ASC`（现状） | 最后一页 | 前 N 页**完全不变** | ✅ 能。热点页天然稳定，甚至只需删末页 |
| `DESC` | **第一页** | **所有页整体偏移** | ❌ 不能。用户发完评论 5 分钟内刷新看不到自己的评论，会以为发送失败 |

**如果采用 DESC + 分页缓存，`add()` 必须主动删缓存**，且"删哪些 key"有三种解法：

1. **枚举删除**——仅在每页条数固定时可行。因为 key 空间收敛为 `1..MAX_CACHE_PAGE`，可以一次批量删：
   ```java
   List<String> keys = new ArrayList<>(MAX_CACHE_PAGE);
   for (int p = 1; p <= MAX_CACHE_PAGE; p++) {
       keys.add(RedisKeys.commentList(noteId, p));
   }
   redisTemplate.delete(keys);   // DEL 支持多 key，1 次 round trip
   ```
2. **版本号**——每页条数可变时的唯一干净解法，O(1) 且不需要枚举：
   ```java
   add() → redisTemplate.opsForValue().increment(RedisKeys.commentListVersion(noteId));
   读    → comment:list:{noteId}:v{version}:{page}
   ```
   旧版本的 key 靠 TTL 自然过期，不必扫描删除。
3. **短 TTL 兜底**——不推荐。DESC 下会导致"自己发的评论自己看不见"，体验不可接受。

**绝不要用 `KEYS` 或 `SCAN` 删通配符**：`KEYS` 会阻塞整个 Redis 实例（O(N) 全库扫描），`SCAN` 虽然不阻塞但游标迭代实现复杂、且无法保证原子性。

## 五、推荐结论

**分两步走，顺序不能颠倒：**

1. **先让接口支持分页**（方案 C 的游标分页）。这是所有缓存策略的前提，且**即使完全不加缓存，它也能单独立竿见影地解决上万条数据的查询性能**。
2. **再缓存第一页**（`comment:list:{noteId}:1`，TTL 5 分钟，空结果 1 分钟）。只有 1 个 key，失效就是删 1 个 key。

**推荐方案 C 的理由**：

- 扫描行数恒定，深分页问题从根上消失（A/B 都解决不了）
- 新增评论不造成分页偏移，不会重复或漏数据（A/B 的固有缺陷）
- 缓存只需 1 个 key，`add()` 的失效逻辑最简单
- 与社区产品"加载更多"的交互天然契合，本来就不需要跳页

**如果产品明确要求页码跳页**（比如"跳到第 8 页"），则退回方案 B，但必须同时接受：① 每页条数服务端固定，② `add()` 枚举删除前 N 页，③ 深分页仍然慢。

**业务层面的补充建议**：评论区只展示前 N 页（如前 50 页），更早的评论引导用户走"查看更多历史评论"的独立接口。这样既满足 99% 用户的浏览需求，又从产品设计上回避了深分页，性价比最高。

## 六、验证方法

Day2 课堂实战的三条验收标准（连访两次 SQL 只打印一次、`GET comment:list:1` 有 JSON 且 TTL 有剩余、发评论后立刻可见）在改造后**仍然适用**，直接复用即可。

针对"上万条"这个新场景，补充验证项：

| 验证目标 | 方法 |
| --- | --- |
| 确认缓存对象不再是大 key | `redis-cli -p 6380 MEMORY USAGE comment:list:1:1`，改造后应降到几 KB |
| 找出实例现存的大 key | `redis-cli -p 6380 --bigkeys` |
| 确认删除没有阻塞 | `redis-cli -p 6380 SLOWLOG GET 10`，观察有无 DEL 造成的慢日志 |
| 确认深分页被解决 | 构造上万行数据后 `EXPLAIN`，游标 SQL 应显示 `rows` 恒等于每页条数 |
| 确认分页不重复不漏 | 边翻页边插入新评论，对比游标方案（无重复）与 offset 方案（会出现偏移） |

其中"构造上万行数据"可以这样快速造：

```sql
INSERT INTO t_comment (note_id, user_id, content)
SELECT 1, 3, CONCAT('压测评论 ', n) FROM
  (SELECT 1 n UNION SELECT 2 UNION ... ) t;   -- 或用存储过程/递归 CTE 生成 1 万行
```

## 附录 A：本次实测记录

环境：Docker 容器 `xhs-redis`（宿主 **6380** → 容器 6379）、`xhs-mysql`（宿主 **3307** → 容器 3306）。
注意宿主机上另有独立的 MySQL(3306) 与 Redis(6379)，其中 6379 需要密码，排查连接问题时要认准 3307/6380。

**A.1 单条评论 JSON 体积**

`redis-cli -p 6380 GET comment:list:1` 取回的实际内容（4 条评论）：

```
["java.util.ArrayList",[["com.xhs.vo.CommentVO",{"id":1,"userId":3,"nickname":"海口吃货","avatar":"","content":"收藏了！下周就去","createTime":[2026,8,20,10,0]}],...]]
```

可见 `activateDefaultTyping` 确实为每个元素写入了 `com.xhs.vo.CommentVO` 全限定类名。按字段逐项计算，短评论单条约 150 字节，据此推算 1 万条约 1.5 MB。

**A.2 Jackson 对不可变集合的处理（实测）**

曾担心 `Collections.emptyList()` 写入缓存后无法反序列化。用项目相同的 `ObjectMapper` 配置（`activateDefaultTyping` + `NON_FINAL` + `JavaTimeModule`）实测，**可以正常往返**：

```
OK       Collections.emptyList()
         ["java.util.Collections$EmptyList",[]]
         => java.util.Collections$EmptyList
OK       Collections.unmodifiableList(new ArrayList<>())
         ["java.util.Collections$UnmodifiableRandomAccessList",[]]
         => java.util.Collections$UnmodifiableRandomAccessList
```

结论：本项目的 Jackson 版本不存在该问题。唯一要注意的是反序列化得到的 `EmptyList` / `UnmodifiableRandomAccessList` / `SingletonList` **都是不可变集合**，如果后续代码对"从缓存取出的列表"做 `add`/`remove` 会抛 `UnsupportedOperationException`（当前代码只读不写，不受影响）。

**A.3 `t_comment` 索引现状**

```sql
CREATE TABLE `t_comment` (
  `id` bigint NOT NULL AUTO_INCREMENT,
  `note_id` bigint NOT NULL,
  `user_id` bigint NOT NULL,
  `content` varchar(500) NOT NULL,
  `create_time` datetime DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  KEY `idx_note` (`note_id`)
) ENGINE=InnoDB
```

即 3.4 节所说的：缺少显式的 `(note_id, id)` 联合索引。

## 附录 B：本文未涉及但已发现的相关问题

1. **`note:{id}` 缓存中的评论数会陈旧**。`add()` 删除了评论列表缓存，但没有删除 `note:{id}`（`CommentService.java:70-73`），而后者的缓存值里含 `commentCount`（`NoteVO.java:20`），TTL 为 30 分钟。结果是发完评论后，**笔记详情页的评论数最长陈旧半小时**。与本挑战同源但属于独立缺陷，按约定只记录不修改。
2. ~~**`CommentService` 中的常量名为 `NOTE_CACHE_MINUTES`**（`CommentService.java:28`），系从 `NoteService` 复制而来，用在评论缓存上语义错位。~~ **已修复**：该常量现已更名为 `COMMENT_CACHE_MINUTES`，本文正文引用的即为更名后的版本。
3. **`ORDER BY create_time` 缺少唯一字段兜底**，见 2.5 节。改造时建议至少写成 `ORDER BY create_time DESC, id DESC`。
